One-time read · jobhunt research prompt v0.2

How to make jobhunt's search actually good

A prompt to send to a deep-research session — and a plain-English explainer so you know why every part is there.

In plain English: what is this?

Right now, when you type something in the jobhunt search box, the app does the dumbest thing possible — it looks for that exact string anywhere in the job title, company name, or description. No ranking, no understanding, no "did you mean". A search for "machine learning" matches a job that uses the phrase once in a footer just as well as one that's actually about ML.

The plan for v0.2 is to fix this. There are basically three ways to do it:

  • Stack A — Keep it lexical. Use SQLite's built-in full-text search (FTS5) with BM25 ranking. Boost matches in the title. Blend that score with the current recency-based score. Simple, fast, no AI.
  • Stack B — Lexical first, AI second. Same FTS5 lookup, but then re-rank the top 50 results using sentence embeddings. Better quality, more moving parts, opt-in.
  • Stack C — Full hybrid. Run lexical search and vector search in parallel, then fuse the two ranked lists (RRF). Best quality, most complexity, embeddings always-on.

The research prompt below asks a Claude deep-research session to pick one of those three stacks and defend the choice with concrete numbers — not "depends on your needs", not a textbook overview of BM25, but a real recommendation with latency tables, RAM estimates, and PyInstaller packaging notes.

Why is the prompt so demanding?

This was vetted by a "council" of critique seats. They flagged several traps that the obvious version of the prompt would fall into:

  • Surveys instead of decisions. Asking "what are the options for X?" gets you a Wikipedia article. Asking "name three options and pick one" gets you a decision.
  • Generic IR textbook output. If you don't demand SQL snippets, specific parameter values, and named files in cited projects, you get "BM25 is good for lexical, embeddings are good for semantic" — which you already knew.
  • The PyInstaller trap. A lot of vector libraries don't survive being bundled into a single-file binary on Windows/macOS/Linux. If you don't make the researcher fill in a "PyInstaller: Y/N per OS" cell, they'll silently recommend something that breaks your release pipeline.
  • The hidden frame-shift. The single highest-leverage decision probably isn't "which embedding model" — it's "what text do you embed per job?" Embedding a focused 340-character summary scores roughly 2.3× higher than embedding the same content inside a 1.5KB blob. That question wasn't in the first draft; it's now Tier 1.
  • Scope creep. The original draft had 10 areas (skill extraction, location normalization, query DSLs, dedup, etc.). Most of those are v0.3 concerns and would dilute the research budget for the actual v0.2 decision. They're explicitly deferred below.

What you do with this

  1. Open Claude (or another deep-research tool), paste everything from the "Research prompt" heading down to the end of the file.
  2. Wait for the ~4,500-word answer.
  3. Read the "Bottom line" section first — it should name Stack A, B, or C and recommend one without hedging.
  4. Before writing any code, do the two pre-flight checks: dump today's score_job() distribution from your SQLite, and confirm WAL mode is on.
  5. First implementation step: extract a new retrieval.py module before writing any FTS5 or vector code. That seam survives a future stack escalation.

Research prompt

You are advising on a single, shippable v0.2 redesign of the search-and-retrieval layer of jobhunt — an MIT-licensed, local-first job-board aggregator distributed as a single PyInstaller binary on Win/macOS/Linux. The output of this research is the architectural decision that the operator (solo dev) ships next sprint. Treat this as a design review, not a literature survey.

Project facts (do not relax these)

  • Python 3.11+, FastAPI, HTMX, Jinja2. Single-machine, single-user. Bound to 127.0.0.1.
  • SQLite is the only data store. Postgres / Elasticsearch / Solr / hosted vector DB are out of scope unless the recommendation is "SQLite + extension X" with a defensible argument.
  • Corpus: 1,000–10,000 typical, 50,000 ceiling. Records are short, structured: title, company, location, salary range, 200–800-word JD, JSON skills/languages. Queries are NOT open NL — they are filter + relevance-rank (e.g., "Python jobs, remote, not [company list], ranked by fit to [skill profile]").
  • Updates every few hours via background scrapes (APScheduler) writing to the same SQLite the UI reads.
  • No network calls at query time. Models downloaded once, run offline, CPU only.
  • Shipped as PyInstaller one-file. ANY new dependency must work inside the bundle on Win/macOS/Linux. C-extensions, runtime model downloads, and Rust-built wheels must be flagged.
  • Realistic deploy target: mid-2020 laptop, 8 GB total RAM shared with browser and IDE. Hard app RAM ceiling 1.5–2 GB. Cold-start matters.
  • Implementation budget: ~5–10 focused dev-days for v0.2 search redesign.
  • The user must be able to reason about why a job ranks where it does.
  • The recommendation must be defensible in a public GitHub README paragraph.

Current state

  • Free-text (q): SQLAlchemy Job.title|company|description ILIKE %term%. No tokenization, fielded weighting, phrase, fuzzy, or relevance score.
  • Faceted filters: company, location (substring ILIKE), remote/level/degree (exact), max_years, languages/skills (JSON-text LIKE), posted_within_days, min_cv_match.
  • Sort: score (heuristic, query-independent), posted_at, last_seen, cv_match.
  • score_job() — additive: recency (linear 30d decay) + desc-length-capped + skill-count-capped + lang-count-capped. The free-text q does NOT influence it. Computed at refresh time, stored as scalar.
  • CV match: cosine of full-CV embedding vs per-job (title + first 3000 chars of desc) embedding, all-MiniLM-L6-v2. Job embeddings NOT stored. match_all_jobs() recomputes job vectors every run.
  • Extractors: hardcoded regex/keyword tables for skills, languages, level, remote, degree, min_years.
  • Modules in play: filters.py (Select builder), scoring.py (refresh-time score), cv.py (CV-to-job similarity), refresh.py (scrape + index lifecycle), models.py (SQLAlchemy), main.py (FastAPI routes).

The decision this prompt must resolve

Name exactly THREE mutually exclusive retrieval stacks for v0.2 — labelled Stack A, Stack B, Stack C — that span the realistic option space. Suggested starting frame (revise if a better partition exists):

  • Stack A: Lexical-only — FTS5 BM25 + tokenizer choice + fielded weighting, blended with the existing heuristic score_job(). No vectors, no semantic.
  • Stack B: Lexical-primary + optional semantic re-rank — FTS5 BM25 as retrieval, sqlite-vec / sqlite-vss / fastembed as opt-in re-ranker over the top-K lexical hits. Embeddings stored, incremental.
  • Stack C: True hybrid with RRF fusion — FTS5 BM25 ∥ ANN vector recall, reciprocal-rank-fused into a single ranked list. Embeddings always-on.

For EACH stack, return:

  1. One sentence: what it is.
  2. Implementation cost in dev-days (within 5–10-day budget).
  3. The SINGLE biggest disqualifying risk.
  4. The required latency/RAM/packaging table (below) fully filled in.
  5. Module ownership diff vs current code (below).
  6. The "pick this if…" single-sentence trigger.

Then close with: "Given the constraints above, I recommend Stack [X] because [single reason]." Do NOT hedge with "depending on" qualifiers. If you cannot name a winner, name the single blocking question the operator must answer, and state what each possible answer implies.

Required architectural diff per stack

For each stack, state explicitly:

  1. Module ownership — which existing module (filters.py, scoring.py, cv.py, refresh.py, models.py) absorbs the new logic, OR specify a new module (e.g., retrieval.py) with its public interface signature.
  2. Scoring lifecycle boundary — score_job() is refresh-time and stored; BM25/cosine/RRF are query-time. Name the boundary in code; do not conflate "score" across lifecycles.
  3. Index lifecycle — FTS5 trigger vs explicit population in refresh.py; for vectors, embed-on-insert vs full-reindex. State which refresh.py call site changes; state the failure mode when index falls out of sync.
  4. SQLite concurrency — WAL mode required? Connection-pool changes? Extension loading per-connection vs once? How do background scrape writes coexist with live read queries during refresh?
  5. Migration from current ILIKE — is JobQuery extended (additive) or replaced (breaking)? Which models.py columns change? What is the one-step migration for existing v0.1 users? Do saved searches survive?
  6. Query-time inference — does anything embed at query time? If yes, flag as sync-CPU-bound-inside-async-FastAPI; specify run_in_executor / background-task placement.
  7. Testability — name one unit-testable seam per stack (e.g., "FTS5 query builder testable against in-memory SQLite with FTS5 enabled, no FastAPI harness").
  8. PyInstaller hazards — flag C extensions (sqlite-vec, sqlite-vss/faiss, hnswlib), Rust-built wheels (tokenizers), runtime model downloads, torch shared libs (~1.5–2 GB cold extract). State which require custom hooks.

Concreteness standard (applies to every claim)

A response that names a library without its API, asserts a trade-off without a failure condition, or recommends a parameter without a specific value will not satisfy this prompt. The target reader is implementing this sprint.

  • Show at least one SQL or Python fragment per stack, scoped to: 
    CREATE VIRTUAL TABLE jobs_fts USING fts5(
  title, company, description, skills_json,
  tokenize = '...'  -- you name it
);
-- jobs: id, title, company, description, skills_json TEXT, location,
--       posted_at, last_seen, cv_match, score
  • State every numeric parameter with a specific value and one-sentence rationale: BM25 k1/b, FTS5 column weights (bm25(jobs_fts, w_title, w_company, w_desc, w_skills)), RRF k (default 60 — justify if changed), HNSW ef/M, embedding dimension, cosine threshold for "good match", top-K cutoff. No ranges unless indeterminacy is explicitly proven.
  • Tokenizer choice MUST address: C++, C#, node.js, .NET, Go — the failure modes porter / unicode61 / trigram exhibit on these are the only thing that matters for a job board. Show which tokenizer survives each.
  • For every OSS project cited: name file and function (e.g., ceaksan/hybrid-search src/search.py rrf_fuse()), not just repo.
  • For each stack, state ONE query string it ranks correctly in top-3 AND ONE query string where it produces a wrong/surprising result. Include at least one failure mode specific to JD text (short docs, high vocab overlap between roles, temporal drift of skill terms).

Mandatory research areas (Tier 1 — must answer)

These four areas feed directly into the Stack A/B/C decision. Each is answered IN the per-stack analysis above, not as a standalone survey.

T1. Free-text relevance over SQLite FTS5. BM25 parameters, tokenizer choice (porter / unicode61 / trigram / custom), column weighting for title vs company vs description vs skills_json, phrase support, prefix queries, how FTS5 rank combines with the existing refresh-time score_job() WITHOUT conflating lifecycles.

T2. Vector store on SQLite (only if Stack B or C is recommended). Head-to-head: sqlite-vec, sqlite-vss, fastembed-only (no store, in-mem numpy), chromadb-embedded. Required axes: install footprint, indexing time at 50k, ANN recall vs exact, P99 query latency, PyInstaller one-file viability on Win/macOS/Linux, C-extension/Rust dependency chain. Default assumption: sqlite-vec is most likely winner; prove or disprove.

T3. Embedding model for short structured JD text. Order axes BY PyInstaller bundle impact FIRST, then accuracy. Compare: all-MiniLM-L6-v2 (via sentence-transformers AND via fastembed/onnxruntime — these have radically different RSS), bge-small-en-v1.5, e5-small-v2, nomic-embed-text-v1.5. Required: warm RSS after first inference (NOT weight-file size), CPU encode latency batch=1 at 256 tokens, MTEB retrieval score (specifically short-text/asymmetric tasks, not paragraph QA), license (MIT/Apache only), PyInstaller bundle delta. fastembed+ONNX is the expected PyInstaller winner — prove or disprove.

T4. Embedding unit per job record (frame-defining; do NOT skip). What text gets embedded per job? Compare: (a) full JD, (b) title + extracted skills + normalized location as a derived short string, (c) title + first N chars of JD (current cv.py behaviour), (d) curated structured summary (title + company + skills + JD first paragraph). Reference the known empirical finding that focused 340-char chunks score ~2.3× higher cosine similarity than 1.5KB multi-topic docs carrying the same information (ceaksan/hybrid-search measurement). This decision likely dominates retrieval quality more than model choice.

Secondary areas (Tier 2 — answer only if budget remains; ≤400 words total)

T5. Rank explainability — how to surface "why is this job #3?" in HTMX without bloating UI. Score-component breakdown vs feature attribution. One concrete template.

T6. Negative-filter expressions (-company:X, NOT remote, python AND NOT django) — survey job-search-native approaches (jobspy, indeed -keyword syntax, LinkedIn search), NOT RAG diversity. Compare FTS5 NOT operator vs JOIN-based blocklist table vs structured field exclusion.

Explicitly out of scope this session (defer to v0.3)

  • Query intent routing / NL-to-filter extraction — UX layer, not retrieval architecture; doesn't change v0.2 stack choice.
  • Skill/language extraction beyond current regex — data-pipeline / ETL concern; orthogonal to retrieval.
  • Location normalization, GeoNames, "Remote – EU" parsing — scraper/ETL concern; doesn't change retrieval.
  • Result diversity / MMR / near-dup dedup — post-retrieval; depends on which Stack ships; premature without that anchor. (Re-open for v0.3 with JobFunnel-anchored framing.)
  • LLM re-ranking at query time (latency budget).
  • Cloud APIs, telemetry, LinkedIn/Indeed integrations, Postgres migration.

Comparable-project rules

A "comparable project" must satisfy at least TWO of: (a) runs entirely offline without a background server, (b) searches short structured records (not long docs/passages), (c) distributed as binary or single-file install. Known partial comparables: ceaksan/hybrid-search (closest structural match), AIngram, sqlite-rag, Llamail (curated-embedding-unit lesson), Sonar (Obsidian plugin, BGE choice). Note: NO published OSS exists that is (PyInstaller-distributed AND job-aggregator AND has measured retrieval numbers). JobFunnel is the only domain match and is archived/undocumented — flag this gap, do not fabricate numbers. Do NOT cite a general RAG-over-documents demo as evidence for a job-search retrieval choice.

Source constraints

  • Primary docs and OSS with >1k stars preferred.
  • Benchmark numbers MUST be cited with hardware reference or marked "unverified".
  • Recency floor 2023; flag pre-2023 claims with sanity check.
  • Distinguish general IR / RAG-over-passages from short-form structured recruiting text. Apply Llamail-style scepticism: full-text embedding of noisy JDs underperforms curated-field embedding.

Output shape

  • Markdown, target 4,500 words. Cap at 5,000.
  • Lead with "Bottom line for jobhunt": Stack A/B/C named, table populated, recommendation sentence, single biggest counter-argument to the recommendation.
  • Then Tier 1 areas T1–T4 (folded into the per-stack analysis).
  • Then Tier 2 areas T5–T6 if budget permits (skip silently if not).
  • End with "What I am NOT confident about" — and for the recommended stack, state the SINGLE most plausible argument against it; if that argument is correct, which alternative stack wins, and what would the operator need to verify to know.
